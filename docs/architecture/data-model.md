# Data model and migrations

Status: **foundation in place (#52), auth tables (#53), trips with idempotency and audit (#61).** This doc owns the database conventions. Entities and relationships are in [`domain-model.md`](domain-model.md). Decisions: [ADR-0002](adr/0002-monorepo-and-stack.md) and [ADR-0006](adr/0006-api-and-application-layer.md).

## Where things live

```
packages/db/
  src/schema/           Drizzle table definitions (one file per area; exported from index.ts)
  migrations/           Committed SQL, plus meta/ (journal and snapshots, generated by drizzle-kit)
  src/config.ts         DATABASE_URL validation (the only place that reads process.env)
  src/client.ts         connectDatabase(url) → { db, pool, close }
  src/migrate.ts        runMigrations() with an advisory lock
  src/admin.ts          create/drop/recreate helpers, local-only guards
  src/testing/          createTestDatabase / withTestDatabase (exported as @globetrot/db/testing)
  scripts/              migrate.ts and reset.ts
```

Only adapters touch the database. `packages/domain` never does, and `packages/application` reaches it through ports (ADR-0006).

## Conventions

| Topic | Rule |
|---|---|
| Names | `snake_case`, **singular** table names (`trip`, `user_preference`), `<table>_id` foreign keys |
| Ids | Domain tables use **UUIDv7 generated in application code**, stored as `uuid`: time-sortable, not guessable, known before insert. Better Auth tables keep its id format. Never expose serial ids |
| Instants | `timestamptz` in UTC. Every table has `created_at`, and mutable ones have `updated_at` |
| Calendar dates | `date`, with no time zone (trip days, departure), as in [`i18n.md`](i18n.md) |
| Money | `amount_minor BIGINT` + `currency CHAR(3)` ([`money.md`](money.md)). Exchange rates are `NUMERIC(20,10)`. Never `float` or `numeric` for amounts |
| Enumerations | `text` with a `CHECK (... IN (...))` built from the same `as const` list the domain uses. Avoid PostgreSQL enum types, because changing them is awkward in migrations |
| Ownership | A user-owned table has `owner_id uuid NOT NULL` referencing the user. Rows are private by default and only reachable through application operations that check the actor |
| Geography | `geography(Point, 4326)` for places and pins, with a GiST index ([places spike](spikes/places.md)) |
| Deletion | Not implemented until specified. Archive with a status instead of deleting |

## Authentication tables

`user`, `session`, `account`, `verification` and `rate_limit` come from Better Auth (migration `0001_auth_tables`) and keep its text ids and its column shapes; the rest of the conventions above still apply (singular snake_case names, `timestamptz`). `user.email` is stored lowercase and a CHECK constraint enforces it. Behaviour, configuration and the trust model: [`authentication.md`](authentication.md).

## Trips, idempotency and audit

Migration `0002_trips` (and `0003_audit_event_append_only`). Code: `packages/db/src/schema/trip.ts`, the SQL in `src/repositories.ts`.

| Table | What | Notes |
|---|---|---|
| `trip` | A user's trip | `id uuid` (UUIDv7 from the application), `owner_id text` → `user.id`, `title`, `start_date date` (nullable), `currency char(3)`, `status`, `visibility`, `created_at`, `updated_at`. Index `(owner_id, created_at)` |
| `idempotency_key` | A mutation already done | Primary key `(owner_id, key)`, canonical request `fingerprint`, stored `response` (jsonb) |
| `audit_event` | Append-only history of mutations | `actor_kind`, `actor_id`, `action`, `entity_type`, `entity_id`, `metadata` (jsonb), `occurred_at` |

- **`owner_id` is `text`, not `uuid`,** because it references Better Auth's `user.id` (a text id). The "Ownership" rule above otherwise holds. The foreign key is `ON DELETE RESTRICT`: deleting an account that has trips fails instead of silently destroying them. Account deletion and its retention rules are specified separately.
- **The database enforces the rules too,** not only the application: title trimmed and 1–120 characters, `currency` matches `^[A-Z]{3}$`, `status` and `visibility` are in their lists (built from the same `as const` arrays as the domain, so they cannot drift). `visibility` only allows `private` until sharing is specified; widening a CHECK is a one-line migration.
- **`status` is stored, the journey `stage` never is** (it is derived, [`business-rules.md`](../product/business-rules.md#trips)).
- **`audit_event` cannot be changed:** a trigger rejects `UPDATE`, `DELETE` and `TRUNCATE` (a superuser can still disable triggers; the guard is against the application's own connection). `actor_id` has **no foreign key** on purpose, so the history survives the account. `metadata` carries field names, never values: no personal data.
- **`idempotency_key` rows are written in the transaction of the work they guard.** A visible key therefore always has its response, and two concurrent requests with the same key serialize on the unique row. Old rows are only useful for a retry window and can be cleaned by a job later.

## User preferences

Migrations `0004_user_preferences` and `0005_theme_and_motion_preferences`. One row per user in `user_preference` (primary key `user_id`, `ON DELETE CASCADE`: it is settings, not history).

| Column | Rule |
|---|---|
| `locale` | One of the supported languages (CHECK from `SUPPORTED_LOCALES`). Default `en` |
| `currency` | ISO 4217 code, `char(3)`, default `USD`. The default for **new** trips; existing trips keep their own |
| `home_country`, `nationality` | ISO 3166-1 alpha-2, `char(2)`, nullable |
| `time_zone` | IANA name, nullable. Stored in the platform's spelling (`america/sao_paulo` becomes `America/Sao_Paulo`) |
| `units` | `metric` or `imperial`, default `metric` |
| `theme` | `day`, `red-eye` or `system` (follow the operating system), default `system` (CHECK from `THEME_CHOICES`) |
| `motion` | `full` or `reduced`, default `full` (CHECK from `MOTION_CHOICES`). The OS's reduced-motion setting wins over `full` at display time, so it is not stored |

- **Independent by construction.** Nothing derives one column from another, and the update writes only the columns it is given (`INSERT ... ON CONFLICT DO UPDATE SET <given columns>`). Choosing Portuguese cannot move the currency or the country.
- **The row is created at sign-up** with the language the person was using, read from the `globetrot_locale` cookie ([`authentication.md`](authentication.md)). If it is missing (the hook failed, or an account predates #58), `getPreferences` answers with the defaults and the first save creates the row.
- Country and time-zone validity is checked in the application (`isCountryCode`, `canonicalTimeZone` in `@globetrot/domain`); the database checks the shape and the closed lists.

## Destinations (a trip's route)

Migration `0006_trip_destinations`. One row per stop in `destination`, `trip_id` references `trip` with `ON DELETE CASCADE` (a trip is never deleted today, but its route must never outlive it).

| Column | Rule |
|---|---|
| `id` | UUIDv7 made by the application |
| `position` | 0-based order on the route, never negative. The whole route is replaced together, so positions are always `0..n-1` |
| `place_key` | The client's stable key for the place (`geoapify:<id>`, `catalog:tokyo`), 1 to 200 characters. **Not** a foreign key: the places table arrives with the geocoder |
| `name` | 1 to 200 characters |
| `country_code` | ISO 3166-1 alpha-2, upper case, nullable |
| `region` | Free text, nullable |
| `latitude`, `longitude` | `double precision`, CHECKed to -90..90 and -180..180 |
| `nights` | 0 to 365, default 0 (day trips are 0) |

- **Replace, don't patch.** `replaceDestinations` deletes the trip's rows and inserts the list in order inside one transaction (with the audit entry), so a failed save leaves the old route intact and sending the same route twice changes nothing. At most 100 stops (`MAX_DESTINATIONS`).
- **State** (`planned` or `draft`, for Pip proposals) and the link to a places table are added by the migrations of the features that need them.
- The audit entry (`destination.replace`) holds the **number** of stops, never which places: where someone plans to go is personal.

## Budget: expenses and savings

Migration `0007_budget_and_savings`. Both tables reference `trip` with `ON DELETE CASCADE`. Amounts are `bigint` **minor units** (`mode: 'bigint'`), never floats, and cross the API as exact decimal strings ([money.md](money.md)).

| `expense` column | Rule |
|---|---|
| `category`, `status` | CHECKed against the domain lists (`EXPENSE_CATEGORIES`, `EXPENSE_STATUSES`: estimate, confirmed, paid, unknown) |
| `description` | Trimmed, 1 to 120 characters |
| `amount_minor`, `currency` | What was typed: positive, in the currency the person chose |
| `trip_amount_minor` | The same cost in the **trip's currency**, positive. This is what totals add up. Equal to `amount_minor` when the currencies match |
| `fx_rate`, `fx_source`, `fx_as_of` | Provenance of the conversion: 1 `currency` = `fx_rate` trip currency, where it came from (`manual` today) and the day. **All three or none**: a rate without its source and day is refused by a CHECK |

- **The server converts.** The client sends the amount and, for another currency, the rate; the converted amount is always computed by `convert` from the domain, never read from the request. A cost too small to be worth one minor unit after converting is refused.
- `trip_savings` is one row per trip: `saved_minor` and `monthly_minor` in the trip's currency, never negative.
- **The trip's currency is locked once there is money in it.** `PATCH /v1/trips/{id}` with another currency answers `422` (`currency_locked`) while the trip has a cost or non-zero savings, because every stored amount is in that currency. It can change freely before that.
- Audit entries (`expense.create`, `.update`, `.delete`, `savings.update`) hold the category and status, never an amount or a description.

## Checklists

Migration `0008_checklists`. `checklist_item` references `trip` with `ON DELETE CASCADE`.

- `group` is CHECKed against the domain list (`CHECKLIST_GROUPS`: documents, money, bookings, packing). `label` is trimmed, 1 to 120 characters. `done` defaults to false.
- Items keep the order they were added (`created_at`, then `id`). A batch add spaces its items one millisecond apart so they keep their order.
- A trip keeps at most 100 items (enforced by the application, `CHECKLIST_MAX_ITEMS`).
- **The readiness stamps are not stored.** `getChecklist` evaluates the domain's `milestones` from the route, costs, savings and items every time, so a stamp can come back off. Recording first-time stamps with their date (`recordStamps`), the visa page history and the celebration are still to do. `stays` and `itin` cannot be earned yet: they need costs per stop and activities per day.
- Audit entries (`checklist.add`, `.update`, `.delete`) hold groups, the changed field names and a count, never a label (a label can be a passport number or a booking code).

## Extensions

The first migration (`0000_extensions.sql`) enables `postgis`, `pg_trgm` and `unaccent`, using `IF NOT EXISTS`. The local Docker init script (`infra/postgres/init/`) enables the same ones as a convenience, and production relies on the migration.

`postgis` needs a superuser or a pre-created extension. On a managed database, create it once by hand and the migration becomes a no-op. The Postgres container on Coolify runs the application user as superuser, so no manual step is needed there.

## Migrations

- **Forward-only.** Never edit a migration that was applied anywhere. Fix mistakes with a new one.
- **Generate:** edit `src/schema`, run `pnpm --filter @globetrot/db generate`, review the SQL and commit it **with** `migrations/meta/`. For hand-written SQL (extensions, data fixes, special indexes) use `pnpm --filter @globetrot/db exec drizzle-kit generate --custom --name=<what>`.
- **Check:** `drizzle-kit check` runs inside the package's `lint`, so CI fails if the journal and snapshots are inconsistent.
- **Apply:** `pnpm --filter @globetrot/db migrate`. Drizzle applies all pending migrations in one transaction, and a PostgreSQL advisory lock makes concurrent runners (several replicas starting together) take turns. Running again when nothing is pending changes nothing.
- **Compatible with the previous release.** Deployments overlap, so the old app version keeps running while a migration applies. Use expand/contract: add the new column or table first, ship code that uses it, then remove the old one in a later release.
- **Bundled apps** (`apps/api`, `apps/worker`) must ship `packages/db/migrations` and pass its location to `runMigrations(handle, folder)`, because the default path is relative to the source file. Where migrations run in production (app start or a release step) is decided in the production-readiness milestone (M11).

## Local database

- `pnpm services:up` starts PostgreSQL + PostGIS ([`local-development.md`](../engineering/local-development.md)), and `pnpm --filter @globetrot/db migrate` brings it to the latest migration.
- `pnpm --filter @globetrot/db reset` drops and recreates the database named in `DATABASE_URL`, then migrates. It **refuses** any host other than `localhost`, `127.0.0.1` or `[::1]`, and refuses `NODE_ENV=production`.

## Testing against a real database

Integration tests are named `*.int.test.ts` and run with `pnpm test:int` (they need `pnpm services:up` locally). They never touch your development data: `createTestDatabase()` creates `globetrot_test_<random>` on the local server, applies every migration and hands back a client, and `drop()` removes it. `withTestDatabase(fn)` does both around a callback and drops the database even when the callback throws.

```ts
import { withTestDatabase } from '@globetrot/db/testing';

it('does something with a real schema', () =>
  withTestDatabase(async ({ db, pool }) => {
    // db is a Drizzle client, pool is the underlying pg Pool
  }));
```

CI runs the same tests in the `Integration (Postgres)` job against a `postgis/postgis:17-3.7` service container ([`git-workflow.md`](../engineering/git-workflow.md#required-checks)).
