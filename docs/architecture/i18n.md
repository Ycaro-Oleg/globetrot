# Internationalization

Status: **approved** ([ADR-0008](adr/0008-internationalization.md)).

## Supported languages

`en` (source language) and `pt-BR` from day one. The architecture allows adding locales by adding a catalog, with no code changes.

## Rules

- **No user-facing string in components.** This covers copy, validation messages, errors, toasts, aria-labels, emails, notifications and Pip UI text.
- Messages use **ICU MessageFormat** (plurals, select, number/date arguments) and live in `packages/i18n/messages/{locale}.json`, keyed by feature (`board.panel.removeStop`).
- Web uses `next-intl`. React Native uses `use-intl` (same core). The API and worker use the same catalogs for emails and notifications.
- A missing key in any shipped locale fails CI.
- Format dates, numbers, currencies, units and lists with `Intl`, using the user's locale, never string concatenation.
- **Locale ≠ currency ≠ country.** See [`money.md`](money.md).
- Geographic names come from `Place.names[locale]` (GeoNames alternate names), falling back to the English name and then the local name.
- Trip and itinerary dates are **local dates**, with no timezone. Timestamps are stored in UTC and shown in the user's timezone.
- Layout uses CSS logical properties (`margin-inline-start`), so RTL is possible later. Fonts get fallbacks for non-Latin scripts.
- Design for pt-BR expansion (+20–35%). Storybook shows every component in both languages.
- Pip responds in the user's language, and its structured change-list labels are localized.

## URL strategy

- **Marketing pages:** locale prefix (`/en/…`, `/pt-BR/…`) with `hreflang`, for SEO.
- **App:** the locale comes from the user's preference, with no prefix needed.

## The `@globetrot/i18n` package

```
packages/i18n/
  messages/en.json      Source catalog (English): defines every key
  messages/pt-BR.json   Must have exactly the same keys, placeholders and tags
  src/                  Locales, typed keys, formatters, catalog validator
  scripts/check-messages.ts
```

| Export | Use |
|---|---|
| `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, `isSupportedLocale` | The interface languages (`en`, `pt-BR`). `en` is the source and the fallback |
| `negotiateLocale(tags)`, `parseAcceptLanguage(header)` | Pick the UI language from user preferences. An exact match wins, then the same language (`pt-PT` → `pt-BR`, `en-GB` → `en`). It **never** implies a currency or country |
| `catalogs`, `Messages`, `MessageKey` | The catalogs and their types. `MessageKey` is the union of dot paths, e.g. `'nextSteps.planEmptyDays'` |
| `formatMessage(locale, key, values)` | Formatting outside React: emails, notifications, worker, API errors. Rich-text tags render as plain text. The web app uses next-intl with the same JSON |
| `formatLocalDate(date, locale, options?)`, `formatYearMonth(month, locale)` | Time-zone-free calendar dates and months ("April 2027" / "abril de 2027"). Money is formatted with `formatMoney` from `@globetrot/domain` |
| `validateCatalogs(source, catalogs)`, `describeProblem` | Catalog consistency rules, used by the CI check and tests |

### Adding or changing a string

1. Add the key to `messages/en.json`, under the feature it belongs to (`board.panel.removeStop`). Use ICU syntax for anything that varies:
   - plurals with an `other` branch, and `=0` when zero reads differently. pt-BR treats 0 as singular ("0 dia"), so add `=0` there;
   - `select` for enums;
   - `{n, number}` for numbers;
   - `<strong>…</strong>` tags for emphasis.
2. Add the same key to `messages/pt-BR.json`, with the **same placeholders and tags**. Write natural Brazilian Portuguese, not a literal translation.
3. Pass preformatted values for money (`formatMoney`) and dates (`formatLocalDate`/`formatYearMonth`). Keep units and currency out of the message text.
4. Run `pnpm --filter @globetrot/i18n check` (it also runs inside `pnpm lint`).

**CI fails** when a locale is missing a key or has an extra one, when ICU syntax is invalid (including a plural or select without `other`), when a message is empty, or when placeholders or tags differ from the source. A missing key also fails `tsc`, because each catalog is typed as `Messages`.

### Adding a locale

Add the tag to `SUPPORTED_LOCALES` in `src/locales.ts`, create `messages/<tag>.json` and register it in `src/catalog.ts`. Stored preferences are constrained in the database too, so also add a migration that widens `user_preference_locale_valid` (and drop the old CHECK in the same migration). The check then requires it to be complete. Agree on a translation workflow (human review) before shipping a third locale (ADR-0008).

## Email

Transactional emails use the `email` namespace of the catalogs. `renderEmail(template, locale, data)` in `@globetrot/application` returns the subject, a plain-text body and a simple HTML body, all from the same strings; a test checks that both versions carry the same content in both languages. Rules: no remote images, no tracking pixels or tracked links, one call-to-action link, everything interpolated is escaped, and the link must be `http(s)`. The language is the user's stored preference, then the language cookie sent at sign-up, then English ([`authentication.md`](authentication.md#email-verification-and-recovery)). Adding a template: add its strings (`<template>.subject`, `body`, `action`, `expiry`, `ignore`) to every catalog, add the name to `EmailTemplate`, and the template tests then cover it.

## Web integration (`apps/web`)

The web app uses [next-intl](https://next-intl.dev) 4 (App Router) with the shared catalogs. There is **no locale-prefixed routing yet**: the app takes the locale from a preference. Prefixed marketing URLs arrive with the landing page (M8).

| File | Role |
|---|---|
| `i18n/request.ts` | `getRequestConfig`: resolves the locale (stored preference, then cookie), returns `messages` from `@globetrot/i18n` `catalogs` and the user's `timeZone` (UTC when none) |
| `i18n/locale.ts` | `LOCALE_COOKIE`, `resolveWebLocale()` (supported value → itself, anything else → `en`) and `chooseLocale()` (stored language first, then the cookie) |
| `lib/stored-preferences.ts` | `sessionCookieHeader()` and `fetchStoredPreferences()`: the server-side call to `GET /v1/me/preferences` with only the session cookie, a 2 s timeout, and `null` on any failure |
| `app/settings/` | The provisional settings page: `page.tsx` (loads the stored values), `settings-view.tsx` (the form, built with `@globetrot/ui`), `options.ts` (country, currency and time-zone lists in the user's language) |
| `app/actions.ts` | `setScaffoldLocale` (writes only the cookie) and `savePreferences` (the settings form: PATCHes the API as the signed-in user, then aligns the cookie with the stored language) |
| `app/layout.tsx` | `<html lang>` from the resolved locale, wrapped in `NextIntlClientProvider` |
| `next.config.ts` | `createNextIntlPlugin('./i18n/request.ts')`, plus `@globetrot/i18n` in `transpilePackages` |

- **How the locale is chosen.** A **signed-in user's stored language wins**. The `globetrot_locale` cookie is what an anonymous visitor has, and the fallback when a signed-in user's settings cannot be read (API down or slow, expired session). Nothing else is consulted. The cookie holds a value from `SUPPORTED_LOCALES`. It is `httpOnly`, `SameSite=Lax`, valid for a year, `Secure` in production and scoped to `/`. An absent, tampered or unsupported value falls back to `en`.
- **No guessing.** `Accept-Language` is deliberately **not** read here. A detected language is only a suggestion the user confirms ([business rules](../product/business-rules.md#locale-and-currency)), so `negotiateLocale` will feed the onboarding suggestion instead. Preferences persist since #58 ([`api-contracts.md`](api-contracts.md), `user_preference`): the stored language replaces the cookie for signed-in users, and the cookie remains the anonymous fallback. Anonymous requests make no API call. For a signed-in request the web server asks the API once, forwarding **only** the session cookie.
- **The sign-up language.** The API reads the language cookie once, when an account is created, and stores it as the new account's language (see [`authentication.md`](authentication.md)). The currency, country, nationality and time zone start empty or at the defaults (USD, none).
- **Saving the language** from the settings page updates the stored value **and** the cookie, so signing out keeps the language the person chose.
- **Language is independent of everything else.** The action writes only the language cookie. Tests assert that no other cookie is set and that the rendered scaffold shows no currency or country.
- **Time zone.** `timeZone` is the user's stored time zone when they set one, and `UTC` otherwise. Without it next-intl warns about server/client markup mismatches. Trip dates stay calendar dates with no time zone either way.
- **Copy.** Components call `useTranslations('feature')` (server and client components alike), and every string lives in the shared catalogs. The two language names ("English", "Português (Brasil)") are intentionally the same in both locales, so people can find their own language.
- **Known limit.** `NextIntlClientProvider` currently inherits the full catalog, so all messages ship to the client. Pass only the namespaces a client component needs once bundle size matters.
- **Testing.** Render with `NextIntlClientProvider` and `renderToStaticMarkup` (see `app/page.test.tsx`), and mock `next/headers` for actions (`app/actions.test.ts`). `apps/web/vitest.config.ts` sets `oxc.jsx.runtime: 'automatic'` because the app's tsconfig keeps `jsx: preserve` for Next.js.
